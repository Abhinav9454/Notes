0.1 Welcome to Spring Boot: What is Spring Boot & Why Do We Use It?

Orientation

Spring Boot is an open-source, Java-based framework used to develop standalone, production-ready enterprise applications with minimal manual configuration. It fundamentally simplifies the creation of backend services, RESTful APIs, microservices, and modern web applications.

Real-World Analogy: E-Commerce Backend System

Imagine you want to build an Amazon or Flipkart-like e-commerce application. The backend needs to manage:

  • Products & Categories: Managing product catalogs, variants, and stock inventory.
  • Users & Authentication: User registration, login, JWT security, and role permissions.
  • Shopping Carts: Session carts, item quantity, and cart persistence.
  • Orders & Payments: Checkout calculation, payment gateway webhooks, and invoice generation.
  • Database Operations: High-speed relational queries, transactions, and connection pooling.

Building all these components from scratch in traditional Java requires thousands of lines of boilerplate setup. Spring Boot provides pre-configured tools and starter libraries that help you develop these backend features efficiently.

6 Core Reasons Why We Use Spring Boot:

  1. Less Configuration: Drastically reduces tedious manual setup and eliminates XML configuration files.
  2. Auto-Configuration: Analyzes classpath dependencies and automatically wires sensible default beans.
  3. Embedded Server: Ships with embedded Apache Tomcat, Jetty, or Undertow — no external server deployment needed.
  4. Rapid REST API Development: Provides clean annotations (@RestController, @GetMapping) to build HTTP endpoints in seconds.
  5. Effortless Database Integration: Direct integration with MySQL, PostgreSQL, and Oracle via Spring Data JPA and Hibernate.
  6. Production Support & Metrics: Built-in health checks, operational metrics, and environment auditing through Spring Boot Actuator.
HelloController.java (Your First Spring Boot REST API) 
package com.example.notes;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/hello")
    public String sayHello() {
        return "Hello, Spring Boot!";
    }
}

When the application starts, sending a GET request to http://localhost:8080/hello immediately returns:
Hello, Spring Boot!

1. Introduction to Spring Boot: What, Why & Where is it Used?

Foundations

Spring Boot is an open-source Java framework built on top of the Spring Framework that simplifies the development of standalone, production-ready enterprise applications. It fundamentally eliminates manual configuration, allowing developers to focus on writing clean business logic rather than boilerplate setup.

Real-World Analogy: E-Commerce Application Backend

Consider an e-commerce platform like Amazon or Flipkart. The frontend can be built using React, Angular, Vue, or modern HTML/CSS/JavaScript. The frontend communicates with the Spring Boot backend APIs to handle:

  • User Registration & Login: Managing accounts, password hashing, and JWT tokens.
  • Product & Category Management: Searching, filtering, and catalog queries.
  • Shopping Cart Operations: Adding items, quantity updates, and cart persistence.
  • Order Processing: Calculating totals, checkout flows, and invoice generation.
  • Payment Gateway Integration: Processing webhooks from Stripe, Razorpay, or PayPal.
  • Database Communication: High-performance queries and transactions with MySQL/PostgreSQL.

Why Was Spring Boot Introduced? (6 Core Goals)

Before Spring Boot, building a Java web application required configuring XML files (applicationContext.xml, web.xml), hunting down compatible library versions, and configuring external Tomcat/WebLogic servers. Spring Boot was created with 6 revolutionary goals:

  1. Reduce Boilerplate Configuration: Zero mandatory XML configuration.
  2. Simplify Dependency Management: Curated Starters with version BOM (Bill of Materials).
  3. Start Applications Quickly: Launch in seconds directly from the IDE.
  4. Enable Standalone Deployment: Run anywhere with an embedded server as a Fat JAR.
  5. Provide Sensible Default Configurations: Auto-configure beans based on classpath inspection.
  6. Support Production Monitoring & Management: Built-in Actuator health and metrics endpoints.

5 Fundamental Features of Spring Boot:

FEATURE A

Auto-Configuration

Automatically configures Spring beans based on the JAR libraries present on the project classpath and settings in application.properties.

FEATURE B

Starter Dependencies

Convenient dependency descriptors (e.g. spring-boot-starter-web) that bundle compatible libraries without version conflicts.

FEATURE C

Embedded Server

Ships with embedded Apache Tomcat, Jetty, or Undertow. Run directly without deploying a WAR file to a standalone server.

FEATURE D

Standalone Fat JAR

Packages all application classes, libraries, and Tomcat into a single runnable JAR executed via java -jar demo.jar.

The 4 Core Technology Pillars:

🌱 Spring Boot

The framework used to configure, bootstrap, and run Java applications with sensible defaults and minimal manual configuration.

☕ Java (JDK 21)

The core programming language used to write business logic, OOP classes, methods, data models, and enterprise rules.

📦 Apache Maven

The build & dependency manager that downloads starter libraries, compiles source code, runs automated tests, and packages JARs.

🗄️ MySQL Database

The relational database engine used to persistently store users, products, categories, orders, and transactional records.

How Does Spring Boot Work? (Layered Architecture Flow)

[Client / Frontend: React / Browser / Postman] │ Sends HTTP GET /products ▼ [Controller: ProductController] │ Receives HTTP request, maps route, validates request ▼ [Service: ProductService] │ Executes business rules, tax calculations, security checks ▼ [Repository: ProductRepository] │ Spring Data JPA translates method to SQL query ▼ [MySQL Database] │ Retrieves stored product records from relational tables ▼ [Response Pipeline] │ Database ➔ Repository ➔ Service ➔ Controller ➔ Client (as JSON)

Where Is Spring Boot Used in the Real World?

Spring Boot is the #1 framework powering backend services across the global tech industry:

  • E-Commerce Backend Systems: Amazon, Walmart, and Target order-management platforms.
  • Banking & Financial Platforms: High-security transactional banking APIs, fraud detection, and ledger systems.
  • RESTful Web Services & Microservices: Distributed microservices communicating via JSON REST or gRPC.
  • Inventory Management Systems: Real-time warehouse tracking, supply chain ERPs.
  • Authentication & Authorization Services: Centralized OAuth2 and JWT single sign-on (SSO) providers.
  • Enterprise Cloud Applications: Large scale SaaS platforms deployed on AWS, Azure, and Kubernetes.

Key Points to Remember:

• Spring Boot is built directly on top of the Spring Framework — it simplifies, not replaces.
• Auto-configuration reduces manual setup by evaluating classpath dependencies.
• Starter dependencies bundle compatible libraries without version mismatch errors.
• Embedded servers eliminate external Tomcat installation and WAR deployment headaches.
• Controller, Service, and Repository layers neatly organize enterprise backend code.

Spring Framework vs Spring Boot (Detailed Comparison)

Interview aur real-world development dono mein Spring aur Spring Boot ke difference ko clear samajhna bohot zaroori hai:

Feature Traditional Spring Framework Spring Boot
Primary Goal Dependency Injection aur loose coupling provide karna. Spring applications ki development speed aur simplicity badhana (Rapid Application Development - RAD).
Configuration Heavy XML configuration ya lengthy @Configuration classes zaroori hoti hain. Auto-Configuration: Classpath inspect karke sensible defaults automatically set kar deta hai.
Web Server External web server install karna padta hai (Tomcat, Jetty) aur .war file deploy karni hoti hai. Embedded Web Server: Tomcat/Jetty JAR file ke andar hi packed rehta hai. Sirf java -jar se run ho jata hai.

Monitoring & Metrics Koyi built-in solution nahi; custom code likhna padta hai. Spring Boot Actuator: Ready-to-use production health endpoints (/actuator/health, /metrics).
Bootstrap Time Naya project set up karne mein ghanton lagte the. Spring Initializr se 2 minute mein fully running project create ho jata hai.
Analogy (Samajhne ka simple udaharan): Spring Framework ek car engine aur parts jaisa hai jise aapko khud assemble karna padta tha. Spring Boot ek pre-assembled fully functional luxury car hai — aapko sirf key ghumani hai aur drive karna shuru karna hai!

4. Understand the `pom.xml` File

pom.xml (Project Object Model) Maven ka core configuration file hai. Iske zariye Maven samajhta hai ki project ko kaise compile, test aur package karna hai, aur kaunse external libraries download karni hain.

pom.xml — Simplified Annotated Example 
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" 
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 
         https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <!-- 1. Parent POM: Manages dependency versions, plugin configs, and default settings -->
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.4</version>
        <relativePath/> <!-- Lookup parent from repository -->
    </parent>

    <!-- 2. Project Coordinates -->
    <groupId>com.example</groupId>
    <artifactId>demo</artifactId>
    <version>0.0.1-SNAPSHOT</version>
    <name>demo</name>
    <description>Demo Spring Boot Application</description>

    <!-- 3. Java Version Property -->

Understanding the project structure is one of the most important steps in learning Spring Boot. A. src/main/java

Main Java source-code directory. Aapke backend ke saare Java classes, interfaces, records, controllers, services, aur repositories yahan banaye jaate hain.

package com.example.demo.entity;

@Entity

}

5. Dependency Management in Spring Boot: pom.xml, Starters, Scopes & Transitive Dependencies

Dependencies & Build

Dependency Management Spring Boot ka ek fundamental pillar hai. Yeh aapki application ko external libraries ko add, organize, update aur maintain karne mein madad karta hai bina version conflicts ke.

Spring Boot projects mein Maven (ya Gradle) dependencies manage karta hai, jabki Spring Boot unke compatible versions ko automatically synchronize rakhta hai.

1. What Is a Dependency? (Library kya hoti hai?)

Ek dependency ek external library ya module hota hai jise aapka project kisi specific task ko perform karne ke liye use karta hai, taaki aapko har cheez scratch se khud na likhni pade.

For example, agar aap ek E-Commerce Backend bana rahe hain:

  • REST APIs banane ke liye: spring-boot-starter-web
  • Database queries ke liye: spring-boot-starter-data-jpa
  • MySQL database se baat karne ke liye: mysql-connector-j
  • Login aur Security ke liye: spring-boot-starter-security
  • Boilerplate code (getters/setters) kam karne ke liye: lombok
Real-Life Analogy (Makaan banane ka udaharan): Jab aap ghar banate hain, to aap eent (bricks), cement, bijli ke taar (wiring), aur plumbing pipes factory se khareed kar laate hain, khud nahi banate. Isi tarah ek Spring Boot application alag-alag features ke liye ready-made libraries use karti hai — yahi libraries uski dependencies hoti hain!

2. What Is Maven?

Maven Java ecosystem ka sabse popular build automation aur dependency management tool hai.

1. Auto Download: Maven Central repository se required libraries automatically fetch karta hai.
2. Transitive Resolution: Libraries ki aapas ki dependencies ko automatically solve karta hai.
3. Compile: Java source code (.java) ko bytecode (.class) mein compile karta hai.
4. Automated Tests: Build ke dauran JUnit 5 test cases execute karta hai.
5. Packaging: Poore project ko ek single standalone Fat JAR ya WAR file mein pack karta hai.
6. Plugin Management: Custom tasks aur build lifecycle plugins manage karta hai.

Maven ka central configuration file hota hai: pom.xml (POM = Project Object Model).

Pehle traditional Spring mein agar aapko web API banani hoti thi, to aapko 10-12 alag-alag JARs (Spring Core, Spring Web, Spring MVC, Jackson Core, Jackson Databind, Tomcat Embed Core, etc.) manually add karne padte the. Spring Boot mein aapko sirf 1 starter add karna hota hai!

6. Understanding Dependency Versions (Managed vs Overriding)

Spring Boot ka sabse bada benefit hai Curated Dependency Management (BOM).

  • Managed Version: Jab aap spring-boot-starter-web add karte hain to aapko <version> nahi dena padta. Parent POM Spring Boot 3.3.4 ke sath fully tested compatible Jackson, Tomcat, aur Spring Core versions select karta hai.
  • Manually Overriding Versions: Agar aap kisi dependency ka version manually override karte hain bina compatibility check kiye, toh incompatibility errors, NoSuchMethodError, ya ClassNotFoundException aa sakta hai!
Best Practice: Always let Spring Boot manage versions whenever possible. Version tabhi override karein jab aapke paas koi specific security patch ya business requirement ho aur aapne compatibility verify kar li ho.

9. Dependency Conflicts & Resolution

Kabhi-kabhi do alag-alag libraries same third-party library ke alag-alag versions require karti hain (e.g. Library A requires Library X v1.2, but Library B requires Library X v1.5). Is condition ko Dependency Conflict kehte hain.

Maven conflicts ko resolve karne ke liye "Nearest Definition Wins" rule use karta hai (dependency tree mein jo project root ke sabse kareeb ho).

Conflict Troubleshoot Karne Ka 5-Step Process:
  1. Terminal mein run karein: .\mvnw.cmd dependency:tree
  2. Output mein conflicting library ka name search karein.
  3. Check karein ki kaunsi parent dependency use introduce kar rahi hai.
  4. Spring Boot compatibility check karein.
  5. Agar zaroorat ho to conflicting dependency ko <exclusions> tag se exclude karein.

8. `@Controller` vs `@RestController` (In-Depth Comparison)

Spring Boot applications develop karte waqt in dono annotations ka fark samajhna fundamental requirement hai:

Feature@Controller@RestController

12. Next Level: Enterprise CRUD REST Controller with `ResponseEntity<T>`

Jab aap enterprise backend develop karte hain, toh raw strings return karne ke bajaye hamesha ResponseEntity<T> return kiya jata hai. Kyun?

  • Custom HTTP Status Codes set karne ke liye (jaise 201 CREATED naye resource ke liye, 204 NO CONTENT delete ke liye).
  • Custom HTTP Headers pass karne ke liye (Location headers, pagination metadata, custom tokens).
  • Type-safe generic JSON response body provide karne ke liye.

Neeche ek complete real-world enterprise REST controller ka example dekhiye jo sabhi standard HTTP CRUD methods implement karta hai:

ProductController.java (Enterprise CRUD REST Controller) 
package com.example.ecommerce.controller;

import com.example.ecommerce.dto.request.CreateProductRequest;
import com.example.ecommerce.dto.response.ProductResponse;
import com.example.ecommerce.service.ProductService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductService productService;

    // Constructor Injection (Best Practice)
    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    // 1. GET ALL: Fetch all products (HTTP 200 OK)
    @GetMapping
    public ResponseEntity<List<ProductResponse>> getAllProducts() {
        List<ProductResponse> products = productService.getAllProducts();
        return ResponseEntity.ok(products);
    }

    // 2. GET BY ID: Fetch single product by path variable (HTTP 200 OK)
    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getProductById(@PathVariable Long id) {
        ProductResponse product = productService.getProductById(id);
        return ResponseEntity.ok(product);
    }

    // 3. POST: Create new product with validation (HTTP 201 Created)
    @PostMapping
    public ResponseEntity<ProductResponse> createProduct(@Valid @RequestBody CreateProductRequest request) {
        ProductResponse created = productService.createProduct(request);
        return new ResponseEntity<>(created, HttpStatus.CREATED);
    }

    // 4. PUT: Update existing product (HTTP 200 OK)
    @PutMapping("/{id}")
    public ResponseEntity<ProductResponse> updateProduct(
            @PathVariable Long id, 
            @Valid @RequestBody CreateProductRequest request) {
        ProductResponse updated = productService.updateProduct(id, request);
        return ResponseEntity.ok(updated);
    }

    // 5. DELETE: Remove product by ID (HTTP 204 No Content)
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteProduct(@PathVariable Long id) {
        productService.deleteProduct(id);
        return ResponseEntity.noContent().build();
    }
}

1. What is Debugging? (Types of Errors in Spring Boot)

Debugging ek aisi process hai jisme hum program ke andar bugs/errors ko khojte (find), unka reason samajhte (understand), aur unhe theek (fix) karte hain.

Consider this simple Java example:

Division Example

    return a / b;
}

Agar aap call karein divide(10, 0);, toh Java runtime ArithmeticException: / by zero throw karega kyunki integer division by zero mathematically invalid hai. Debugging helps you find exactly where the error occurs, why it happens, and how to gracefully handle it.

5 Core Error Categories in Spring Boot:
Error TypeMeaning & NatureReal-World Spring Boot Example
1. Compile-Time Error Java compiler code ko bytecode (.class) mein convert nahi kar pata. Syntax errors, missing semicolon, galat package import, ya unresolved dependency class.
2. Runtime Error Code compile ho jata hai par application run karte waqt unexpected exception throw hoti hai. NullPointerException, ArithmeticException, ClassCastException.
3. Logical Error Code bina kisi crash ya error ke execute hota hai, par output galat hota hai. Discount calculation ka formula ulta ho jana (e.g. price + discount instead of subtraction).
4. Configuration Error application.properties ya environment variables mein invalid settings. Galat server port, malformed JDBC database URL, ya invalid active profile name.
5. Integration Error Dono components individual sahi hain par aapas mein communicate nahi kar pa rahe. Spring Boot MySQL database se connect nahi kar pa raha (Connection Timeout ya Bad Credentials).

2. Understanding the 5-Step Systematic Debugging Process

🔄 The Professional 5-Step Debugging Cycle:
1. Reproduce the Problem: Identify the exact HTTP request, URL, query param, or payload that triggers the failure.
2. Inspect Logs & Exceptions: Check IntelliJ console or terminal logs to find the exact exception type and stack trace.
3. Set a Breakpoint: Pause program execution right before the suspected failure line.
4. Find the Root Cause: Inspect live in-memory variables and trace the execution flow line by line.
5. Fix & Test: Implement the clean fix, rerun tests, and ensure no regressions occurred.

6. What Happens Internally? (The Two ClassLoaders Architecture)

Pura Java JVM restart hone mein 10-15 seconds lag sakte hain kyunki use saare hundreds of external JARs (Spring Framework, Hibernate, Apache Tomcat, Jackson) dobara read karne padte hain.
Spring Boot DevTools is restart process ko ultra-fast banane ke liye Two ClassLoaders use karta hai:

1. Base ClassLoader (Static Libraries)

Yeh un saari 3rd-party dependencies ko load karta hai jo development ke dauran kabhi change nahi hoti (e.g. Spring, Tomcat, Hibernate). Yeh memory mein hamesha loaded rehta hai.

2. Restart ClassLoader (Your Code)

Yeh sirf aapke application classes (target/classes) ko load karta hai jo actively edit ho rahi hain.

Jab aap code change karte hain: DevTools pure JVM ko restart nahi karta, balki purane Restart ClassLoader ko memory se discard karke naya Restart ClassLoader create karta hai. Base ClassLoader pehle se ready rehta hai, isliye restart 1-2 seconds mein complete ho jata hai!

12. Introduction to Dependency Injection (DI) in Spring Boot

Core Architecture

Dependency Injection (DI) Spring Framework aur Spring Boot ka sabse important foundation pattern hai. Yeh application code ko loosely coupled, reusable, maintainable, aur unit testing ke liye super easy banata hai.

🎯 Remember for Interviews: "Dependency Injection is a technique in which an object's dependencies are provided externally rather than created by the object itself. In Spring Boot, the Spring IoC container automatically manages this process."

1. What is Dependency Injection?

Dependency Injection (DI) ek aisi technique hai jisme koi object apne required dependencies (doosre collaborating objects) ko khud create nahi karta; balki ek external source (Spring IoC Container) use required dependencies supply (inject) karta hai.

Imagine you are building an e-commerce application:

  • OrderService — Processes customer orders.
  • PaymentService — Handles payments.
  • EmailService — Sends order confirmation emails.

OrderService ko order complete karne ke liye PaymentService ki zaroorat hoti hai. Manual object creation ke bajaye Spring Boot is dependency ko automatically provide kar deta hai.

❌ Without Dependency Injection:

OrderService controls how its dependency is created using new PaymentService(). Problem: High tight coupling, hard to modify or mock during tests.

✅ With Dependency Injection:

Spring IoC Container creates and manages objects. OrderService receives PaymentService from outside. Benefit: Loosely coupled and easily swappable.

🍳 The Restaurant Analogy: Think of DI like a professional restaurant: a chef needs ingredients to prepare a dish. Instead of farming vegetables and producing every ingredient personally, the chef receives them from external suppliers. In the same way, a Java class receives its dependencies from an external provider (such as the Spring IoC Container), rather than building them itself!

2. What is a Dependency?

A dependency is an object or component that another class needs to perform its work.

PaymentService.java & Tightly Coupled OrderService.java 
public class PaymentService {
    public void pay() {
        System.out.println("Payment successful!");
    }
}

public class OrderService {
    private PaymentService paymentService;

    public OrderService() {
        // Tightly coupled: OrderService creates its own dependency using new!
        this.paymentService = new PaymentService();
    }

    public void placeOrder() {
        paymentService.pay();
        System.out.println("Order placed successfully!");
    }
}

Here, PaymentService is a dependency of OrderService. The problem is that OrderService creates its own object using new, which tightly couples the two classes. Spring Boot offers a better approach: let Spring create and inject the dependency!

3. What are the Main Concepts Behind DI?

A. Dependency

An object that another class needs to perform its work (e.g., PaymentService needed by OrderService).

B. Inversion of Control (IoC)

Control over creating and managing objects is transferred from application code to the Spring framework container.

C. Spring IoC Container

The central container that creates and manages beans, resolves dependencies, and injects them where needed.

4. How Dependency Injection Works in Spring Boot

Spring uses an IoC (Inversion of Control) container to create and manage objects. Objects managed by Spring are called beans.

🔄 The 4-Step Spring DI Process:
1. Spring scans your application ──► Finds components annotated with @Component, @Service, etc.
2. Spring creates bean objects ──► Manages their lifecycle inside the IoC container.
3. Spring resolves dependencies ──► Finds the required bean for each component.
4. Spring injects the dependency ──► The dependent class can now use it directly!

4. Implement Dependency Injection Step by Step

Let's build a working example using constructor injection, the recommended default for required dependencies.

Step 1: src/main/java/com/example/demo/service/PaymentService.java 
package com.example.demo.service;

import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    public String processPayment() {
        return "Payment processed successfully!";
    }
}
  • @Service tells Spring that this class is a service component.
  • Spring registers it as a bean when component scanning includes its package.
  • processPayment() contains the payment business logic.
Step 2: src/main/java/com/example/demo/service/OrderService.java 
package com.example.demo.service;

import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final PaymentService paymentService;

    // Single constructor: Spring automatically supplies PaymentService bean
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public String placeOrder() {
        String paymentResult = paymentService.processPayment();
        return "Order placed successfully. " + paymentResult;
    }
}
  • You do not write new PaymentService() here. Spring passes the managed bean into the constructor.
  • Why use final? It guarantees the reference is initialized during construction and cannot be reassigned later (immutability & thread safety).
  • Since there is only one constructor, Spring does not require @Autowired on it.
Step 3: src/main/java/com/example/demo/controller/OrderController.java 
package com.example.demo.controller;

import com.example.demo.service.OrderService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/orders")
    public String placeOrder() {
        return orderService.placeOrder();
    }
}

5. Types of Dependency Injection

Injection TypeCode PatternWhen to Use & Recommendation
1. Constructor Injection public OrderService(PaymentService ps) { this.ps = ps; } ⭐ Recommended Default. Supports immutability (final), makes dependencies explicit, and simplifies unit testing with mocks.
2. Setter Injection @Autowired public void setPaymentService(PaymentService ps) { this.ps = ps; } Useful when a dependency is optional or intentionally replaceable at runtime.
3. Field Injection @Autowired private PaymentService ps; 🚫 Discouraged. Harder to unit test (requires reflection), dependencies are implicit, and hides circular dependencies.

6. What is `@Autowired`?

@Autowired tells Spring to resolve a dependency and inject a matching bean. When a class has exactly one constructor, Spring automatically uses it for dependency injection, so you can safely omit @Autowired.

7. What if Multiple Implementations Exist?

Suppose you have two payment services: CardPaymentService and UpiPaymentService both implementing PaymentService. Spring throws NoUniqueBeanDefinitionException unless disambiguated:

  • @Primary: Identifies the preferred default bean.
  • @Qualifier("beanName"): Specifies the exact bean name to inject (e.g., @Qualifier("upiPaymentService")).

Spring seamlessly manages dependency injection across all these collaborators!

  • IoC transfers object-management control from application code to the Spring framework.
  • Spring IoC Container creates, wires, and manages Spring beans throughout their lifecycles.
  • @Service, @Repository, and @Component register classes as beans via component scanning.
  • Constructor injection using private final fields is the recommended best practice for required dependencies.

13. Constructor Injection in Spring Boot

Industry Best Practice

Constructor Injection is a type of Dependency Injection (DI) in which a class receives its required dependencies through its constructor.

In Spring Boot, constructor injection is the #1 recommended gold standard because it makes dependencies explicit, supports immutable final fields, and makes unit testing effortless.

🎯 Interview Definition: "Constructor Injection is a dependency injection technique in which required dependencies are provided through a class constructor. In Spring Boot, the Spring IoC container resolves and supplies those dependencies when creating beans."

1. What is Constructor Injection?

Suppose you are building an e-commerce application:
• OrderService handles customer orders.
• PaymentService processes transactions.

OrderService needs a PaymentService object to complete an order. With constructor injection, we pass the PaymentService object through the OrderService constructor:

Constructor Injection Syntax 
public OrderService(PaymentService paymentService) {
    this.paymentService = paymentService;
}

Here, PaymentService is the dependency, and the constructor receives it from outside the class.

2. Step-by-Step Java Example (Plain Java)

Notice how constructor injection works naturally in plain Java without any framework:

Step 1: PaymentService.java 
public class PaymentService {

    public void processPayment() {
        System.out.println("Payment processed successfully!");
    }
}
Step 2: OrderService.java 
public class OrderService {

    private final PaymentService paymentService;

    // Constructor Injection
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void placeOrder() {
        paymentService.processPayment();
        System.out.println("Order placed successfully!");
    }
}
Key Lines Explained:
  • private final PaymentService paymentService;: Declares a dependency that cannot be reassigned after construction (immutability).
  • OrderService(PaymentService paymentService): Receives the dependency through the constructor.
  • this.paymentService = paymentService;: Stores the received object into the instance field.
  • placeOrder(): Uses the injected object to process the payment safely.
Step 3: Main.java — Testing with Plain Java 
public class Main {

    public static void main(String[] args) {

        PaymentService paymentService = new PaymentService();

        // Injecting paymentService into OrderService via constructor!
        OrderService orderService = new OrderService(paymentService);

        orderService.placeOrder();
    }
}

3. Constructor Injection in Spring Boot

In a real Spring Boot application, you don't call new in Main.java. Spring's IoC container automatically creates and injects these objects:

14. Setter Injection in Spring Boot

Setter Injection is a type of Dependency Injection (DI) in which a class receives its dependencies through a setter method after the object has been created.

In Spring Boot, Setter Injection is useful when a dependency is optional or needs to be changed after object creation. For required dependencies, Constructor Injection is generally preferred.

1. What is Setter Injection?

Suppose you are developing an e-commerce application.

  • OrderService manages customer orders.
  • EmailService sends order confirmation emails.

The OrderService needs an EmailService object. Instead of receiving it through a constructor, it receives it through a setter method.

The basic syntax is:

public void setEmailService(EmailService emailService) {
    this.emailService = emailService;
}

Here, setEmailService() is the setter method used to inject the dependency.

2. Step-by-step Java example

Step 1: Create EmailService.java

public class EmailService {

    public void sendEmail() {
        System.out.println("Order confirmation email sent!");
    }
}

This class contains the email functionality.

Step 2: Create OrderService.java

public class OrderService {

    private EmailService emailService;

    // Setter Injection
    public void setEmailService(EmailService emailService) {
        this.emailService = emailService;
    }

    public void placeOrder() {
        System.out.println("Order placed successfully!");

        if (emailService != null) {
            emailService.sendEmail();
        }
    }
}

Understand the important lines:

  • private EmailService emailService; declares the dependency.
  • setEmailService() receives the EmailService object.
  • this.emailService = emailService; stores the received object.
  • The null check allows the order to be placed even if no email service has been provided.

Step 3: Create Main.java

public class Main {

    public static void main(String[] args) {

        OrderService orderService = new OrderService();

        // Create dependency
        EmailService emailService = new EmailService();

        // Inject dependency using setter
        orderService.setEmailService(emailService);

        // Use the service
        orderService.placeOrder();
    }
}

Output:

Order placed successfully!
Order confirmation email sent!

Notice the sequence:

  1. Create the OrderService object.
  2. Create the EmailService object.
  3. Call setEmailService() to inject the dependency.
  4. Call placeOrder().

This is Setter Injection in plain Java.

3. Setter Injection in Spring Boot

15. The Spring IoC Container

The Spring IoC Container is one of the most important concepts in Spring Framework and Spring Boot. It is responsible for creating objects, managing them, configuring them, and injecting their dependencies.

IoC stands for Inversion of Control.

Let's understand it step by step with Java code and a Spring Boot example.

1. What is the Spring IoC Container?

The Spring IoC Container is a component of the Spring Framework that manages the lifecycle of objects called Spring Beans.

Normally, in Java, we create objects ourselves using the new keyword. With Spring, we can give the framework responsibility for creating and managing those objects.

For example, without Spring:

PaymentService paymentService = new PaymentService();

With Spring, we can declare a class as a bean:

@Service
public class PaymentService {
}

Spring can then create and manage the PaymentService object automatically when the application starts.

In simple words: The Spring IoC Container acts like a manager that creates and supplies the objects your application needs.

2. Why do we need the IoC Container?

Imagine you are developing an e-commerce backend with these classes:

  • ProductController
  • ProductService
  • ProductRepository
  • PaymentService
  • EmailService

Without Spring, you might need to create and connect all these objects manually. As your project grows, this becomes difficult to maintain.

With Spring, the container manages these objects and their dependencies.

Spring IoC Container

Creates, configures and manages beans

ProductController
ProductService
ProductRepository
PaymentService

The container resolves dependencies between managed components.

3. What is a Spring Bean?

A Spring Bean is an object that is created, configured, and managed by the Spring IoC Container.

For example:

import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    public void pay() {
        System.out.println("Payment successful!");
    }
}

Here, @Service tells Spring that this class is a service component. When component scanning finds it, Spring registers and manages a corresponding bean.

Other common annotations that register components as beans include:

Annotation Purpose
@Component General-purpose Spring component
@Service Service or business-logic component
@Repository Data-access component
@Controller MVC controller
@RestController REST API controller

These annotations are specialized forms of Spring's component registration mechanism. The class must be discovered through component scanning for this approach to work.

4. How does the Spring IoC Container work?

The process generally follows these steps:

Step 1: Application starts — Spring Boot initializes the application context.
↓
Step 2: Finds bean definitions — Discovers components and configuration-defined beans.
↓
Step 3: Creates and configures beans — Instantiates objects and resolves their dependencies.
↓
Step 4: Injects dependencies — Provides required beans through constructors, setters, or other supported injection mechanisms.
↓
Step 5: Application runs — Components use their injected dependencies to handle requests.

For typical singleton beans, Spring creates one shared instance per bean definition in the application context. Other bean scopes can have different lifecycles.

5. Types of Spring IoC Containers

Spring provides two main container interfaces.

A. BeanFactory
BeanFactory is the basic IoC container interface. It provides bean creation, retrieval, and dependency management capabilities.

B. ApplicationContext
ApplicationContext builds on BeanFactory and provides additional enterprise application features, such as event publication, internationalization, and integration with Spring's annotation-based configuration.

In Spring Boot, ApplicationContext is the container you will usually encounter.

7. What is the bean lifecycle?

A bean's lifecycle describes what happens from creation until destruction.

A simplified lifecycle is:

  1. Spring instantiates the bean.
  2. Spring injects its dependencies.
  3. Initialization callbacks run, such as @PostConstruct.
  4. The bean is available for use.
  5. Destruction callbacks run when the container shuts down, such as @PreDestroy for applicable beans.

Example:

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;

@Component
public class DemoService {

    @PostConstruct
    public void init() {
        System.out.println("Bean initialized");
    }

    @PreDestroy
    public void destroy() {
        System.out.println("Bean is being destroyed");
    }
}

In Spring Boot 3.x, use the jakarta.annotation package for these annotations. Destruction callbacks generally run when the application context closes cleanly; they are not guaranteed after every abrupt process termination.

16. Configuring Beans via Annotations

In Spring Boot, bean configuration using annotations means telling Spring which classes or methods should be managed by the Spring IoC Container using annotations such as @Component, @Service, @Repository, @Autowired, @Configuration, and @Bean.

Instead of manually creating every object using the new keyword, you hand over object instantiation and dependency management to the Spring IoC Container.

🎯 Interview Summary: "Spring beans can be configured using component annotations such as @Component, @Service, and @Repository, or explicitly using @Configuration and @Bean. Spring then manages their lifecycle and injects dependencies through mechanisms such as constructor injection."

1. What is a Spring Bean?

A Spring Bean is an object that is created, configured, and managed by the Spring IoC Container.

For example, in a modern e-commerce backend, you typically have these collaborating beans:
• ProductController: Handles HTTP REST requests and endpoints.
• ProductService: Contains core business logic, calculations, and rules.

17. Controlling Bean Selection

Resolution & Conditional Beans

In Spring Boot, Controlling Bean Selection means telling Spring which bean it should inject when multiple beans of the same type or interface are available in the IoC container.

This is a critical concept in Dependency Injection, especially when your application provides multiple implementations of a common business interface (e.g., card payments, UPI, and cash on delivery in an e-commerce backend).

🎯 Interview Definition: "Controlling bean selection in Spring Boot means specifying which bean Spring should inject when multiple beans match a dependency. Common mechanisms include @Primary, @Qualifier, @Profile, and conditional bean registration."

1. Understanding the Problem: Ambiguous Bean Dependencies

Suppose you have a common payment processing interface:

PaymentService.java 
public interface PaymentService {
    void pay();
}

Now, let's create two concrete implementations annotated with @Service:

CardPaymentService.java & UPIPaymentService.java 
import org.springframework.stereotype.Service;

@Service
public class CardPaymentService implements PaymentService {
    @Override
    public void pay() {
        System.out.println("Payment using Card");
    }
}

@Service
public class UPIPaymentService implements PaymentService {
    @Override
    public void pay() {
        System.out.println("Payment using UPI");

OrderService.java (Ambiguous Injection Point)

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;

Spring inspects the container and finds two matching beans of type PaymentService (cardPaymentService and upiPaymentService). Because neither is marked as primary and the constructor parameter does not specify a qualifier, Spring aborts startup with:
NoUniqueBeanDefinitionException: expected single matching bean but found 2: cardPaymentService, upiPaymentService

@Service
public class UPIPaymentService implements PaymentService {

19. Externalizing Configuration

App Configuration & Profiles

Externalizing Configuration means keeping application settings outside your Java source code so you can modify behavior across environments (local development, QA, staging, and production) without recompiling or rebuilding the application.

For example, in an e-commerce backend, you connect to a local MySQL database during development, but connect to an encrypted cloud database (AWS RDS) in production. Instead of hardcoding credentials in Java classes, you define them in external properties or environment variables.

🎯 Interview Definition: "Externalized configuration is the practice of keeping application settings outside the Java source code, using sources such as properties files, YAML files, environment variables, and command-line arguments. It allows the same application to run in different environments with different settings, improves maintainability, and helps keep sensitive configuration out of source code."

1. Why Do We Need Externalized Configuration?

Consider this hardcoded Java snippet:

❌ Anti-Pattern: Hardcoded Configuration 
String appName = "My E-Commerce App";
String paymentMode = "TEST";
int maxOrders = 100;

If you need to change paymentMode from TEST to LIVE, you would have to edit the Java file, recompile the JAR, run unit tests, and redeploy.

✨ Key Benefits of Externalized Configuration:
  • Zero Code Changes: Modify operational parameters without touching source code.
  • Multi-Environment Parity: Seamless transitions between Development, Staging, and Production.
  • Secret Protection: Critical credentials (passwords, JWT secrets, Stripe API keys) are kept out of Git repositories.
  • DevOps & Docker Friendly: Cloud platforms (Kubernetes, AWS ECS) can inject runtime variables directly.

20. Configuring Beans Using Code

In Spring Boot, configuring beans using code means telling Spring how to create and manage objects using Java configuration classes instead of relying only on annotations such as @Component or @Service.

The main annotations you need to understand are:

  • @Configuration — marks a class as a source of bean definitions.
  • @Bean — tells Spring to create and register the object returned by a method as a Spring bean.
  • @Autowired or constructor injection — lets one bean receive another bean as a dependency.

1. First, understand what a Spring bean is

Suppose you create an ordinary Java object:

NotificationService service =
        new EmailNotificationService();

You created the object yourself using new.

In Spring Boot, you can instead ask Spring to create and manage the object. A Java object managed by Spring is called a Spring bean.

Spring can then inject that object into other classes, manage its lifecycle, and resolve its dependencies.

2. Create a simple example

Imagine an e-commerce application that needs a payment service.

Create the interface PaymentService.java:

package com.example.demo.payment;

public interface PaymentService {
    void processPayment(double amount);
}

Create the implementation UPIPaymentService.java:

package com.example.demo.payment;

public class UPIPaymentService implements PaymentService {

    @Override
    public void processPayment(double amount) {
        System.out.println(
            "Processing UPI payment of ₹" + amount
        );
    }
}

Notice that we have not added @Component or @Service to UPIPaymentService. We will register it explicitly using Java configuration.

3. Create a configuration class using @Configuration and @Bean

Create AppConfig.java:

package com.example.demo.config;

import com.example.demo.payment.PaymentService;
import com.example.demo.payment.UPIPaymentService;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new UPIPaymentService();
    }
}

Let's understand each part.

@Configuration

@Configuration
public class AppConfig {
}

This tells Spring that the class contains configuration information, including bean definitions.

@Bean

@Bean
public PaymentService paymentService() {
    return new UPIPaymentService();
}

Spring calls this method to obtain the object and registers the returned object as a bean.

By default, the bean's name is the method name: paymentService.

Remember the difference:

  • @Service — registers a class as a bean through component scanning.
  • @Bean — registers the object returned by a method inside a configuration class.

Both approaches can register Spring beans. You usually choose one approach for a particular object, not both.

4. Inject the bean into another class

Create OrderService.java:

package com.example.demo.service;

import com.example.demo.payment.PaymentService;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void placeOrder() {
        System.out.println("Order placed successfully!");
        paymentService.processPayment(1500.0);
    }
}

Spring creates OrderService and injects the PaymentService bean defined in AppConfig.

Because there is only one matching PaymentService bean, no @Qualifier is required.

7. What if we have multiple implementations?

Suppose your application supports UPI and card payments.

@Bean
public PaymentService upiPaymentService() {
    return new UPIPaymentService();
}

@Bean
public PaymentService cardPaymentService() {
    return new CardPaymentService();
}

        PaymentService paymentService) {
    this.paymentService = paymentService;
}

Import:

import org.springframework.beans.factory.annotation.Qualifier;

The qualifier value matches the bean method name.

8. When should you use @Bean?

Use Java-based bean configuration when:

  • You need to register a class from a third-party library that you cannot annotate with @Component.
  • You want explicit control over how an object is constructed.
  • You need to provide constructor arguments or configure an object before registering it.
  • You want to group related configuration in a dedicated configuration class.

For ordinary application services, @Service, @Repository, and @Component are often simpler. For infrastructure objects and third-party integrations, @Bean is especially useful.

21. Lazy Initialization

Lazy Initialization in Spring Boot means creating an object or Spring bean only when it is first needed, rather than creating it during application startup.

In Spring Boot, beans are created eagerly by default in most singleton-bean scenarios. You can use @Lazy to delay the creation of a bean until it is requested.

Let's understand this step by step with Java code.

1. Understand the concept with a real-life example

Imagine your e-commerce application has three services:

  • OrderService — processes customer orders.
  • PaymentService — processes payments.
  • ReportService — generates reports.

Suppose users place orders frequently, but the reporting feature is rarely used.

Without lazy initialization, Spring normally creates singleton beans such as ReportService during application startup, even if no report is requested.

With lazy initialization, you can delay creating ReportService until the first time it is needed.

Eager vs. Lazy initialization
Default
Eager initialization

Bean is created during application startup.

On demand
Lazy initialization

Bean creation is delayed until it is first needed.

2. Example without @Lazy

Create ReportService.java:

package com.example.demo.service;

import org.springframework.stereotype.Service;

@Service
public class ReportService {

    public ReportService() {
        System.out.println("ReportService bean created!");
    }

    public void generateReport() {
        System.out.println("Generating report...");
    }
}

When Spring starts and discovers this class, it normally creates the singleton bean eagerly.

You should see:

ReportService bean created!

This message can appear during application startup, even if generateReport() is never called.

3. Example with @Lazy

Now add @Lazy to the service:

package com.example.demo.service;

import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Lazy
@Service
public class ReportService {

    public ReportService() {
        System.out.println("ReportService bean created!");
    }

    public void generateReport() {
        System.out.println("Generating report...");
    }
}

What changes?

  • Spring registers the bean definition.
  • Spring delays creating the actual bean until it is requested.
  • The constructor message should not appear during startup if nothing requests this bean.

When you eventually call generateReport() through the bean, Spring creates the bean first.

Important: If an eager singleton directly depends on ReportService, Spring may still need to create it during startup to satisfy that dependency. To delay creation across that dependency, use @Lazy at the injection point as well.

4. Using @Lazy with dependency injection

Suppose OrderService depends on ReportService, but reports are needed only occasionally.

package com.example.demo.service;

import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final ReportService reportService;

    public OrderService(@Lazy ReportService reportService) {
        this.reportService = reportService;
        System.out.println("OrderService bean created!");
    }

    public void viewReport() {
        reportService.generateReport();
    }
}

Here, @Lazy on the constructor parameter tells Spring to inject a lazy-resolution proxy. That proxy delays resolving the actual ReportService until a method is invoked on it.

Expected behavior

Application startup:

  • OrderService created — Its constructor runs during startup.
  • ReportService not yet created — The injected proxy postpones resolving the actual service.

When viewReport() is called:

  • ReportService created — Spring resolves the real bean and calls generateReport().

The relevant console messages would be:

OrderService bean created!
ReportService bean created!
Generating report...

The report service's creation message appears when the report is first requested, not merely because OrderService was created.

5. Enable lazy initialization for the entire application

Instead of annotating individual beans, you can enable lazy initialization globally.

In application.properties:

spring.main.lazy-initialization=true

With this setting, Spring Boot delays initialization of most application beans until they are needed.

You can disable it again with:

spring.main.lazy-initialization=false

This setting changes the default initialization behavior for the application, while explicit configuration and framework requirements may still affect individual beans.

6. @Lazy vs. global lazy initialization

Feature @Lazy Global property
Scope Specific bean or injection point Most application beans
Configuration Java annotation application.properties
Control Selective Application-wide default
Best use Delay a particular service Delay initialization across an application

7. Advantages and disadvantages

Advantages:

  • Can reduce application startup time.
  • Avoids creating some beans that may never be used.
  • Useful for expensive services, optional integrations, and infrequently used features.

Disadvantages:

  • First use may be slower because the bean must be initialized then.
  • Configuration errors that would normally appear during startup may be discovered only when the bean is first used.
  • Lazy initialization does not automatically improve overall application performance; it moves some work from startup to first use.

For critical services, eager initialization can be beneficial because startup reveals configuration or dependency problems earlier.

8. Quick revision

  • Eager initialization: Create the bean during startup; this is the usual default for singleton beans.
  • Lazy initialization: Delay bean creation until needed.
  • @Lazy on a bean: Marks that bean for lazy initialization.
  • @Lazy on an injection point: Allows dependency resolution to be deferred using a proxy.
  • spring.main.lazy-initialization=true: Enables lazy initialization as the application-wide default.

22. Bean Scopes in Spring Boot

Bean Scope defines how many instances of a bean Spring creates and how long those instances are shared or managed.

In simple words, bean scope answers two questions:

  1. How many instances of a bean will Spring create?
  2. Who shares those instances, and for how long?

For example, in your e-commerce application, should every customer request use the same OrderService object, or should Spring create a new object for each request?

Bean scopes control this behavior.

1. Types of bean scopes

Spring Framework defines six commonly used scopes:

  1. Singleton (Default) — One bean instance per Spring IoC container.
  2. Prototype — A new instance each time Spring is asked to create or resolve the bean.
  3. Request — One instance per HTTP request.
  4. Session — One instance per HTTP session.
  5. Application — One instance per ServletContext in a web application.
  6. WebSocket — One instance per WebSocket session.

The first two scopes—singleton and prototype—can be used in ordinary Spring applications. Request, session, application, and WebSocket scopes are associated with web-aware application contexts.

2. Singleton scope

Singleton is the default Spring bean scope.

It means Spring manages one instance of a particular bean definition per IoC container, and that instance is shared wherever the bean is injected.

Example:

Create NotificationService.java:

package com.example.demo.service;

import org.springframework.stereotype.Service;

@Service
public class NotificationService {

    public NotificationService() {
        System.out.println("NotificationService created");
    }

    public void send() {
        System.out.println("Sending notification...");
    }
}

Now create a controller that receives the service:

NotificationController.java:

package com.example.demo.controller;

import com.example.demo.service.NotificationService;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class NotificationController {

    private final NotificationService notificationService;

    public NotificationController(
            NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}

If several Spring-managed components inject this NotificationService, they normally receive the same instance.

You can verify this by comparing object references:

System.out.println(service1 == service2);

If both references point to the same singleton bean, the result is:

true

Important: Singleton scope does not mean one instance for the entire JVM in every possible context. It means one instance per bean definition per Spring container.

When should you use singleton?

Use singleton for stateless services such as:

  • OrderService
  • PaymentService
  • ProductService
  • EmailNotificationService

Avoid storing request-specific mutable data in singleton fields. Multiple threads may access a singleton bean at the same time, so shared mutable state can cause concurrency bugs.

3. Prototype scope

Prototype scope tells Spring to create a new bean instance each time the bean is requested from the container.

Use @Scope("prototype") to configure it.

Example:

Create ReportGenerator.java:

package com.example.demo.service;

import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

@Component
@Scope("prototype")
public class ReportGenerator {

    public ReportGenerator() {
        System.out.println("New ReportGenerator created");
    }
}

Now retrieve it twice from Spring:

ReportGenerator report1 =
        context.getBean(ReportGenerator.class);

ReportGenerator report2 =
        context.getBean(ReportGenerator.class);

System.out.println(report1 == report2);

Here, context is an injected or otherwise obtained Spring ApplicationContext.

Expected output:

New ReportGenerator created
New ReportGenerator created
false

Each getBean() call creates a separate instance.

Important difference: Prototype inside a singleton

Suppose you inject a prototype bean directly into a singleton service:

@Service
public class ReportService {

    private final ReportGenerator reportGenerator;

    public ReportService(ReportGenerator reportGenerator) {
        this.reportGenerator = reportGenerator;
    }
}

Spring normally creates ReportService once and injects one ReportGenerator into it when constructing the service. Calling a method on ReportService repeatedly does not automatically create a new prototype bean each time.

If you need a fresh prototype instance per operation, use ObjectProvider<ReportGenerator>:

@Service
public class ReportService {

    private final ObjectProvider<ReportGenerator> provider;

    public ReportService(ObjectProvider<ReportGenerator> provider) {
        this.provider = provider;
    }

    public void generate() {
        ReportGenerator generator = provider.getObject();

        // Use this new generator for this operation.
    }
}

Spring's provider resolves a new prototype instance whenever getObject() is called.

When to use prototype: Objects that hold short-lived, operation-specific state and should not be shared between operations.

4. Request scope

Request scope creates one bean instance for each HTTP request. Components handling the same request can share that request-scoped instance.

For example, you may want to store a request-specific tracking ID.

RequestInfo.java:

package com.example.demo.web;

import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.RequestScope;
import java.util.UUID;

@Component
@RequestScope
public class RequestInfo {

    private final String requestId = UUID.randomUUID().toString();

    public String getRequestId() {
        return requestId;
    }
}

Use it in a controller:

RequestController.java:

@RestController
public class RequestController {

    private final RequestInfo requestInfo;

    public RequestController(RequestInfo requestInfo) {
        this.requestInfo = requestInfo;
    }

    @GetMapping("/request-id")
    public String getRequestId() {
        return requestInfo.getRequestId();
    }
}

Each HTTP request to /request-id will normally return a new ID. If the same request-scoped bean is accessed more than once during one request, its ID remains the same for that request.

Request scope requires a web-aware Spring context. Spring commonly uses a scoped proxy when injecting a request-scoped bean into a singleton controller.

Use it for: Request-specific metadata, correlation IDs, or temporary state associated with a single HTTP request—not long-term user data.

5. Session scope

Session scope creates one bean instance for each HTTP session. The same instance can be reused across multiple requests belonging to that session.

Example: storing a temporary shopping cart for a user's session.

ShoppingCart.java:

package com.example.demo.web;

import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.SessionScope;
import java.util.ArrayList;
import java.util.List;

@Component
@SessionScope
public class ShoppingCart {

    private final List<String> items = new ArrayList<>();

    public void addItem(String item) {
        items.add(item);
    }

    public List<String> getItems() {
        return items;
    }
}

Each HTTP session gets its own ShoppingCart instance. Two different sessions do not share that instance.

Use it for: Short-lived, session-specific state. In a real e-commerce application, persistent cart data often belongs in a database or another shared store instead, particularly when users log in across devices.

6. Application scope

Application scope creates one bean instance per ServletContext in a web application.

ApplicationInfo.java:

@Component
@ApplicationScope
public class ApplicationInfo {

    private final String applicationName = "E-Commerce";

    public String getApplicationName() {
        return applicationName;
    }
}

Spring manages this bean within the web application's servlet context. It can be shared across requests and sessions in that context.

Use it for: Web-application-wide information. Remember that application scope does not automatically share an object across multiple server instances or JVMs.

7. WebSocket scope

WebSocket scope creates one bean instance per WebSocket session.

WebSocketState.java:

@Component
@Scope("websocket")
public class WebSocketState {

    private String currentMessage;

    public String getCurrentMessage() {
        return currentMessage;
    }

    public void setCurrentMessage(String currentMessage) {
        this.currentMessage = currentMessage;
    }
}

This is useful when an application maintains a persistent WebSocket connection, such as a live chat or real-time notification feature. The WebSocket scope requires WebSocket-aware Spring infrastructure.

8. All scopes compared

Scope Instance created for Typical use
singleton Each bean definition per Spring container Stateless services
prototype Each request to create/resolve the bean Operation-specific objects
request Each HTTP request Request tracking data
session Each HTTP session Session-specific state
application Each ServletContext Web-application-wide data
websocket Each WebSocket session Connection-specific state

9. How to configure bean scopes

You can use annotations on component classes:

@Component
@Scope("prototype")
public class ReportGenerator {
}

Or configure the scope on a @Bean method:

@Configuration
public class AppConfig {

    @Bean
    @Scope("prototype")
    public ReportGenerator reportGenerator() {
        return new ReportGenerator();
    }
}

Both examples register a prototype-scoped bean. Choose one registration method for a given bean so that you don't accidentally define the same component twice.

10. Quick revision

  • Singleton: One shared instance per bean definition in a container.
  • Prototype: A new instance each time Spring is asked to resolve the bean.
  • Request: One instance per HTTP request.
  • Session: One instance per HTTP session.
  • Application: One instance per servlet context.
  • WebSocket: One instance per WebSocket session.

For most Spring Boot backend services, singleton scope is the normal choice. Select another scope only when the object's lifecycle or state requires it.

23. Bean Lifecycle Hooks

Bean Lifecycle Hooks in Spring Boot are methods that Spring calls automatically at specific stages of a bean's lifecycle, such as after the bean has been created and dependencies have been injected, or just before the bean is destroyed.

In simple words, lifecycle hooks let you run your own code when a Spring bean starts working or when it is about to shut down.

For example, in your e-commerce backend, you might want to:

  • Load payment configuration when a service starts.
  • Initialize a cache before processing requests.
  • Close a connection or release resources when the application shuts down.

Let's understand this step by step.

1. Understand the Spring bean lifecycle

When Spring creates and manages a bean, it generally follows this sequence:

  1. Bean Instantiation — Spring creates the object.
  2. Dependency Injection — Spring supplies the required dependencies.
  3. Initialization — Initialization callbacks run.
  4. Bean Ready — The bean is available for normal use.
  5. Destruction — Cleanup callbacks run when the container shuts down.

The exact lifecycle contains additional steps, including bean post-processors. This simplified sequence focuses on the hooks you will commonly use.

2. Using @PostConstruct

@PostConstruct marks a method that Spring invokes after dependency injection is complete and before the bean is put into normal service.

Example:

Create PaymentService.java:

package com.example.demo.service;

import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    public PaymentService() {
        System.out.println("1. Constructor called");
    }

    @PostConstruct
    public void initialize() {
        System.out.println("2. PaymentService initialized");
    }

    public void processPayment() {
        System.out.println("3. Processing payment");
    }
}

Expected output:

1. Constructor called
2. PaymentService initialized

The processPayment() message appears only when that method is actually called.

Why use @PostConstruct?

You can use it to:

  • Validate configuration.
  • Prepare in-memory data.
  • Initialize a lightweight cache.
  • Set up internal state after dependencies are injected.

Important: Avoid putting long-running work in initialization methods. It can delay application startup.

In modern Spring Boot applications, import jakarta.annotation.PostConstruct, not the older javax.annotation.PostConstruct.

3. Using @PreDestroy

@PreDestroy marks a method that Spring invokes when the bean is being destroyed as part of the application context's normal shutdown process.

Example:

Create ReportService.java:

package com.example.demo.service;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    @PostConstruct
    public void initialize() {
        System.out.println("ReportService initialized");
    }

    public void generateReport() {
        System.out.println("Generating report...");
    }

    @PreDestroy
    public void cleanup() {
        System.out.println("Cleaning up ReportService");
    }
}

During a normal application startup and shutdown, the output can include:

ReportService initialized
...
Cleaning up ReportService

The ... represents other application activity.

When is @PreDestroy useful?

Use it for cleanup tasks such as:

  • Releasing resources owned by the bean.
  • Stopping an internally managed background task.
  • Closing a custom resource that Spring does not manage itself.

Important: @PreDestroy is not guaranteed to run if the process crashes, is forcibly terminated, or the container does not shut down gracefully. Don't rely on it as the only way to save critical data.

4. Using InitializingBean and DisposableBean

Spring also provides two lifecycle interfaces.

InitializingBean

Implement afterPropertiesSet() to run initialization logic after properties have been set.

import org.springframework.beans.factory.InitializingBean;
import org.springframework.stereotype.Service;

@Service
public class CacheService implements InitializingBean {

    @Override
    public void afterPropertiesSet() {
        System.out.println("CacheService initialized");
    }
}

DisposableBean

Implement destroy() to perform cleanup when Spring destroys the bean.

import org.springframework.beans.factory.DisposableBean;
import org.springframework.stereotype.Service;

@Service
public class ConnectionService implements DisposableBean {

    @Override
    public void destroy() {
        System.out.println("ConnectionService destroyed");
    }
}

These interfaces work, but they couple your application class directly to Spring APIs. For most application code, annotation-based hooks are often easier to read.

5. Using initMethod and destroyMethod with @Bean

Sometimes you configure a bean using Java configuration instead of annotating the class itself. In that case, you can specify initialization and destruction methods in @Bean.

Suppose you have a class:

FileService.java:

package com.example.demo.service;

public class FileService {

    public void initialize() {
        System.out.println("FileService initialized");
    }

    public void close() {
        System.out.println("FileService closed");
    }
}

Register it using AppConfig.java:

package com.example.demo.config;

import com.example.demo.service.FileService;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class AppConfig {

    @Bean(initMethod = "initialize", destroyMethod = "close")
    public FileService fileService() {
        return new FileService();
    }
}

Here:

  • initMethod = "initialize" tells Spring which method to call after bean initialization.
  • destroyMethod = "close" tells Spring which method to call during bean destruction.

The method names must match the actual methods in the class.

Use one clear lifecycle strategy for each bean to avoid duplicate initialization or cleanup logic.

6. Comparing lifecycle hooks

Hook When it runs Typical use
@PostConstruct After dependency injection Initialize internal state
@PreDestroy During normal bean destruction Clean up resources
afterPropertiesSet() After properties are set Initialization using Spring interface
destroy() During bean destruction Cleanup using Spring interface
@Bean(initMethod = "...") After bean creation and configuration Custom initialization method
@Bean(destroyMethod = "...") During bean destruction Custom cleanup method

7. Important behavior to remember

  • Spring singleton beans are normally initialized eagerly unless lazy initialization applies.
  • Prototype beans have a different lifecycle: Spring creates them, but does not manage their complete destruction lifecycle in the same way as singleton beans. In particular, Spring does not automatically call their configured destruction callbacks after handing them to the caller.
  • Destruction hooks run when the Spring container closes normally and manages the bean's destruction.
  • Avoid manually invoking lifecycle methods as a substitute for letting Spring manage the bean.

    name = "users",

10. Step 8 — Implement the business logic

Create service/UserService.java:

package com.example.demo.service;

import com.example.demo.dto.RegisterRequest;
import com.example.demo.dto.UserResponse;
import com.example.demo.entity.User;
import com.example.demo.repository.UserRepository;

import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Locale;

@Service
public class UserService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public UserService(
            UserRepository userRepository,
            PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    @Transactional
    public UserResponse register(RegisterRequest request) {

        String email = request.email()
                .trim()
                .toLowerCase(Locale.ROOT);

        if (userRepository.existsByEmail(email)) {
            throw new IllegalArgumentException(
                    "An account with this email already exists"
            );
        }

        String hashedPassword =
                passwordEncoder.encode(request.password());

        User user = new User(
                request.name().trim(),
                email,
                hashedPassword
        );

        User savedUser = userRepository.save(user);

        return new UserResponse(
                savedUser.getId(),
                savedUser.getName(),
                savedUser.getEmail(),
                "User registered successfully"
        );
    }
}

Understand the flow:

  1. The service normalizes the email address.
  2. It checks whether that email already exists.
  3. It hashes the password using PasswordEncoder.
  4. It creates a User entity.
  5. The repository saves the entity to MySQL.
  6. The service returns a response DTO without the password.

@Transactional makes the registration operation a database transaction. The unique database constraint is still necessary because two concurrent requests could both pass the initial existence check.

11. Step 9 — Create the REST controller

Create controller/UserController.java:

package com.example.demo.controller;

import com.example.demo.dto.RegisterRequest;
import com.example.demo.dto.UserResponse;
import com.example.demo.service.UserService;

import jakarta.validation.Valid;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping("/register")
    public ResponseEntity<UserResponse> register(
            @Valid @RequestBody RegisterRequest request) {

        UserResponse response = userService.register(request);

        return ResponseEntity
                .status(HttpStatus.CREATED)
                .body(response);
    }
}

Important annotations:

  • @RestController — exposes REST endpoints.
  • @RequestMapping("/api/users") — defines the base URL.
  • @PostMapping("/register") — maps HTTP POST requests to the registration method.
  • @RequestBody — converts incoming JSON into RegisterRequest.
  • @Valid — triggers the validation rules on the DTO.
  • ResponseEntity — lets you choose the HTTP status and response body.

A successful registration returns HTTP 201 Created.

Create exception/GlobalExceptionHandler.java:

package com.example.demo.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, String>> handleBadRequest(
            IllegalArgumentException ex) {

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(Map.of("error", ex.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, String>> handleValidation(
            MethodArgumentNotValidException ex) {

        String message = ex.getBindingResult()
                .getFieldErrors()
                .stream()
                .findFirst()
                .map(error -> error.getDefaultMessage())
                .orElse("Invalid request");

        return ResponseEntity
                .badRequest()
                .body(Map.of("error", message));
    }
}

For this beginner exercise, duplicate emails return HTTP 400 Bad Request. In a more polished API, create a dedicated duplicate-email exception and map it to 409 Conflict. Also handle database uniqueness violations, because concurrent registrations can race even after an existsByEmail check.

1. Important concepts at a glance

Topic Key takeaway
Dependency Injection (DI) Spring provides the objects a class needs instead of the class creating them itself.
Constructor Injection Dependencies are provided through a class constructor.
Setter Injection Dependencies are provided through setter methods.
Spring IoC Container Creates, configures, and manages Spring beans.
@Component, @Service Register classes as beans through component scanning.
@Qualifier Selects a specific bean when multiple candidates exist.
@Primary Makes one bean the preferred candidate when no qualifier selects another.
Externalized Configuration Stores settings outside Java code in properties, YAML, or environment variables.
@Configuration and @Bean Register objects through Java configuration.
Lazy Initialization Delays bean creation until the bean is needed.
Bean Scopes Define the lifecycle and sharing of bean instances.
@PostConstruct Runs initialization logic after dependency injection.
@PreDestroy Runs cleanup logic during normal bean destruction.

2. Remember the differences

  • Dependency Injection: Your class receives its dependencies from Spring rather than creating them directly with new.
  • Bean configuration: Use @Service for application services and @Bean when you want to explicitly define how an object is created.
  • Bean lifecycle: @PostConstruct is for initialization; @PreDestroy is for cleanup during normal shutdown.
  • Bean scope: Singleton is the default scope. Prototype creates a new instance for each container lookup; web scopes serve request-, session-, application-, or WebSocket-specific needs.
